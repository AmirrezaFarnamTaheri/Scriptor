Official advisory records were re-read for every retained ID. Each remains INFO Unmaintained, with no patched release and no newly attached vulnerability classification at the reviewed revision.

- [`proc-macro-error` 1.0.4](https://rustsec.org/advisories/RUSTSEC-2024-0370.html) is required by `glib-macros` 0.18.5 and `gtk3-macros` 0.18.2. It executes as build-time procedural macro support in the Linux GTK/Tauri graph. RustSec suggests alternative diagnostics crates; parent migration is required.
- [`atomic-polyfill` 1.0.3](https://rustsec.org/advisories/RUSTSEC-2023-0089.html) comes through `heapless` 0.7.17 in `postcard` 1.1.3's locked compatibility graph. RustSec recommends `portable-atomic`. This review does not assert that every production target enables postcard's heapless support; lockfile presence is retained conservatively until target/feature pruning is verified.
- [`paste` 1.0.15](https://rustsec.org/advisories/RUSTSEC-2024-0436.html) is required by `biblatex` 0.12.0 and `hayagriva` 0.10.1, used by the citation engine and Typst bibliography implementation. It performs build-time macro expansion. RustSec suggests `pastey` or other macro alternatives; changing the dependency identity requires parent adoption and validation.
- [`unic-char-range`](https://rustsec.org/advisories/RUSTSEC-2025-0075.html), [`unic-common`](https://rustsec.org/advisories/RUSTSEC-2025-0080.html), [`unic-char-property`](https://rustsec.org/advisories/RUSTSEC-2025-0081.html), [`unic-ucd-version`](https://rustsec.org/advisories/RUSTSEC-2025-0098.html), and [`unic-ucd-ident`](https://rustsec.org/advisories/RUSTSEC-2025-0100.html), all 0.9.0, remain in `urlpattern` 0.3.0 via `tauri-utils` 2.9.3. RustSec recommends standard character ranges, ICU properties, or unicode-ident depending on the crate; urlpattern/Tauri migration is required before these can be replaced safely.

These eight existing exceptions are re-reviewed by **2026-11-01**, or before the next production tag, whichever comes first. Their retention records a maintenance risk, not proof that the packages are harmless.

### Compatible-resolution investigation

The official crates.io registry API was queried again on 2026-10-02: glib's highest released 0.18 version remains **0.18.5**, lru's highest 0.16 version remains **0.16.4**, and Tantivy's latest stable release is **0.26.2**. GTK 0.18.2 requires glib `^0.18`; Tantivy 0.26.2 requires lru `^0.16.3`. The advisory-patched glib >=0.20 and lru >=0.18.2 versions therefore do not satisfy those parent ranges. There is no compatible released patch that a lockfile-only update can select.

- **glib:** [upstream PR 1343](https://github.com/gtk-rs/gtk-rs-core/pull/1343/files) changes exactly the pointer local to mutable and passes `&mut p` to the variadic C call. The current [upstream 0.18 branch](https://raw.githubusercontent.com/gtk-rs/gtk-rs-core/0.18/glib/src/variant_iter.rs) and the registry 0.18.5 source still have the unfixed code. A reviewed source backport can remove the binary defect while preserving the GTK API, but it requires a reproducible vendored/pinned dependency and optimized Linux iterator regression tests. The old package version would still match RustSec's version warning; changing a version label or suppressing that warning would not be a valid fix.
- **lru/Tantivy:** the [upstream development manifest](https://raw.githubusercontent.com/quickwit-oss/tantivy/main/Cargo.toml) already requires lru 0.18.2, but identifies Tantivy 0.27.0, which is not a published stable upgrade at the review date. A narrowly scoped vendored 0.26.2 parent-manifest migration to the patched lru is a possible remediation, contingent on indexing/store cache tests; selecting unreleased main would introduce unrelated API/dependency changes. The source-specific lack of the vulnerable pop/panicking-key path above provides concrete reachability evidence while the package-level warning remains unsuppressed.
